# Reference

Exact behaviour of the mod, one entry per part. The [README](README.md) says what the mod does for a lead; this file is what it does to the letter. Entries name each other by heading.

## Logging and order

### Message log

Observes every message agents send each other (`session.send`, `session.receive`, and `tool.call` on `SendMessage` as a fallback) and appends `{ts, from, to, summary, length, type, via}` to `<cwd>/.swarm/log.jsonl` (`summary` is the first line; a message that claims carries `claim: {role, target}`). A delivery whose text a recorded send carried (one of the last 200, from the same sender or to the same recipient) is that send's echo and is not logged again, however late the receiver takes it. Each of the mod's own messages to a teammate (stall nudges, wait asks, claim answers, write warnings) starts with `swarm: `, so its recipient does not take it for the lead's; the mod logs each itself, once, as from `swarm`, and keeps its text per recipient until a delivery carries it, so a recipient that takes it minutes and hundreds of sends later adds no `team-lead … via receive` line; the `SendMessage` call Claude Code runs on the lead's loop for one while it is in flight is not logged, so the lead's sent count and edges hold none of them and each counts once in the swarm's totals. They are never read as claims. A message to an address that is neither a teammate nor the lead's (`team-lead`, `main`), such as `lead`, is logged with that `to` and is no message to the lead: no wake and no edge to it in the looks. Every hook calls `next` except the `[WAIT]` refusal below, and each has a fail-open `.catch`.

### Order stamps

Each message a teammate sends another teammate reaches it with `#<n> · HH:MM:SS` (local time, the clock the pane and the text list show too) on its own first line: `n` counts the session's teammate-to-teammate messages as the mod logs them (kept in roster.json and the log's `stamp` field across reloads), so every recipient sees one order; the lower stamp came first. Sends to the lead, broadcasts (`*`, which reach the lead too) and the mod's own carry none.

### Idle notices

Agent Teams sends the lead an `idle_notification` on every teammate stop (native, the mod cannot stop it). The mod counts them per agent (`waits N · <age> ago` in the pane, `idleNotices` in roster.json, a reason other than `available` shown), logs them as `type: "IDLE"`, and keeps them out of message counts and wakes. With the lead filter on, one whose reason is `available` or absent is kept from the lead; one with another reason reaches it.

### File activity

A teammate's Edit, Write, MultiEdit, NotebookEdit and Read calls reach the mod's `tool.call` hook with the teammate's `agentId` (in-process teammates). When the file a teammate last touched changes, its card shows it and the mod appends one `{type: "FILE", from, summary: "✎ hooks/core.ts"}` line to the log; repeated calls on the same file write nothing, and a read of a file the teammate read in the last 5 min shows on the card only. Teams are worked out from messages alone, so file lines never push a team out of the pane's memory. The lead's own calls are not logged.

### Current action

Each tool call a teammate makes shows on its look A card in plain words (`Reading README.md`, `Editing hooks/core.ts`, `Running npm test`, `Searching 'claimOf'`, `Messaging t2`, else `Using <tool>`), cut to the card, kept after the call ends and dim unless the teammate is running, with its call count in the card header (`12×`); it replaces the file on that line. The mod logs it as a `type: "ACT"` line with the count so far, at most one per teammate per 2 s (a call in between shows when that time is up, the latest winning), so a replay shows actions too.

### Refused spawns

A spawn the host or a hook refuses (`agent.spawn` answered with `deny`) shows in look A's message list as `team-lead → kite  REFUSED  teammate limit reached`: from the lead, or from the teammate whose loop asked for it, to the agent's name (its description when it has none), with the reason's first line. The mod logs it as a `type: "REFUSED"` line, which is no message: it adds no sent count, no edge and no team member, and a replay shows it too. A spawn refused to any other subagent is left out.

### Joins and leaves

A teammate's spawn is logged as one `{type: "JOIN", from, summary: "joined"}` line, its end (the agent list reports it completed, failed or killed, or `stop_swarm` stopped it) as one `{type: "LEFT", from, summary: "<status>"}` line; a teammate that had ended before a reload logs none. Neither is a message. In both looks a teammate appears at its JOIN line (in a log without one, at its first line) and is ended from its LEFT line: look A slides its card in from the right over 0.9 s (its bar drawn in cells meanwhile) and greys an ended teammate's card or line; look B fades its star in over 0.9 s and, once it left, down to 35 % of its light over 0.9 s. For 10 s after either, the header says so: `+ joined Kite`, `− left t2`, several in one note (`+ joined Kite, Sage · − left t2`).

## Roster and teams

### Roster

`agent.spawn` (name, model, teammate flag) + `$.agent.list()` every 4 s (status) → `<cwd>/.swarm/roster.json`, readable by any agent. A teammate's first-line `[PROPOSE] hello <Name>` sets its `codeName` (casing as written); roster.json, the pane and the band then show it as `Atlas (t1)`. A later message it sends renames it: another hello, or `I (t3) rename to kite`, `renamed Kite`, `(renamed kite)`, `(now Kite)`, `call me Kite`, `now called Kite`, `I am now Kite`, `I am Kite` (`(now Kite)` and the last two need a capital), `I'm kite from now on`; a name may be quoted (`I rename to "kite"`). A hello or rename that gives a teammate a code name another live teammate already has (any case) gets one ``swarm: [ASK] code name <Name> is already used by <name> (<id>). Send a first-line `[PROPOSE] hello <other name>` to every teammate to take another.`` from the mod; the earlier holder keeps the name and nothing is refused. A delivery received later never reverts a name. Two live agents with the same code name (any case) both show `⚠ dup`: in the text list, on both look A cards and (`⚠`) on both agent buttons. A message sent to a code name instead of a team name (`→ kite`) is logged, counted and drawn as sent to the teammate that took it (of several that took it, the one that has not ended, else the latest started; `stop_swarm` and `/swarm stop` resolve names the same way), so no agent goes by a code name. A teammate whose hello keeps its placeholder (`hello t1`) shows as `t1 (no code name)`.

### Workflow agents

Agents a Workflow script starts (`agent.spawn`'s `workflow.runId`, type `workflow-subagent`) are never in `$.agent.list()`. Each is marked completed when its `turn.complete` arrives; on reload one left pending for over 10 min is completed. The pane shows one line per run, `✓ workflow dev-team · 16 agents` (dimmed under other agents) or `● … · 3 running · 5 pending`; the name comes from the Workflow tool call's result (`workflowName`, `runId`). Any other agent that `$.agent.list()` stops reporting is marked completed.

### History

On load or reload the mod reads roster.json and the last 500 lines of log.jsonl. Lines and agents written in this session (both files carry `session-<first 8 of the session id>`) count as before; those from a previous session or team show dimmed under `── earlier ──` and as `(N earlier)` in the header.

### Swarm

The stall watchdog, the claim watchdog and the lead filter act only once the current team is a swarm: two of its teammates have messaged each other and one of them has not ended. Named agents that only report to the lead (a builder, a checker) are no swarm. `/swarm status` shows `swarm: yes/no`.

### Ended team

A teammate the agent list reports as `completed`, `failed` or `killed` (a stop), or no longer lists, has ended; after a reload, an agent restored from roster.json that the next agent list does not report has ended too. A teammate reported `idle` for over 6 hours with no message, idle notice or status change since, and holding no `[WAIT]` or open claim, is dormant: the pane and the band show it as ended (under `── other agents ──`, out of the agent count and the cards) until it runs again, while the team, its claims, its waits and the watchdogs still count it live. Once every teammate of the current team has, the live pane shows it as ended: `ENDED · t1–t4 · ran 26m` in the header (from the first spawn of its teammates to its last activity; the live looks' clock starts at that spawn) (look B: `■ ended · ran 26m`), every agent as `ENDED` on its card and in the count (`4 · 4 ended`), the clock and the idle counters held at the team's last activity, no claim cards; the claims board is cleared once per team, even while other teammates of the lead stay idle; a team that reuses an ended team's names is a new team for this.

## Claims and watchdogs

### Claims

`[CLAIM] <role> <artefact or slice>` messages (the first word must be `build`, `review` or `research`; any other is no claim) and task-list owners → `claims` in roster.json and a CLAIMS section in the pane: one line per deliverable or slice, `#1 · build Atlas (t1) · review Sage (t2) ✓approve` (`build unclaimed`, `⚠ duplicate`; a first-line `[REVIEW] #n … approve` sets `✓approve`, a `[BLOCK] #n` sets `✗block`, on the build when the builder sent it), then one `other · Atlas (t1): final gate` line with each teammate's task-list claims whose subject starts with no role word. Deliverables come from `Deliverable: <path>` lines in teammate spawn prompts or `/swarm deliverable <path>`; a claim names one by path, file name, trailing segment or `#<n>` (`[CLAIM] build #155 (…)` names `repo#155`). A `[CLAIM]` later in a message (inside a hello, or after a first-line `[RELEASE]`) counts unless it is in quotes or backticks or follows a possessive or my, your, his, her, their, its, the, a, own, confirm, quote(d), send, sends or sent (`Sage's [CLAIM] research parser …`, `please confirm [CLAIM] …`, `they sent [CLAIM] …` report another claim). It counts in the list and in both looks; its log line keeps it as `claim`, so a replay and a reload read it too (a log written before has first lines only, so its replay shows such a claim only when the first line made it). A claim is judged on its target token (the first word after the role word, or the inside of a quoted or bracketed start): when that is empty, holds a `"`, says `please`, or holds a space outside quotes, the claim is a sentence fragment and no claim; else the target is that token alone, cut at a `,`, `;` or `(`, and the words after it never join it (`[CLAIM] research parser (t1, sonnet)` claims `parser`, `[CLAIM] research docs/a.md (t2). Output: …` claims `docs/a.md`), so a slice name of several words counts by its first; claim one quoted (`[CLAIM] research "group A"`). A release is only a first-line `[RELEASE] <target>` or `[WITHDRAW] <target>` (`[WITHDRAW] build docs/a.md` for one role); a first clause, after an optional `<name>:`, `I release <target>`, `I withdraw <target>`, `I drop my claim on <target>`, `I drop my <target> claim` or `Yielding <target> to …`; a first-line sentence `The <target> claim is released to …`; or a first line `[CLAIM] <role> <target> is withdrawn …` (or `is released`), which is no claim. A first line `[CLAIM] <role> <target> is (already) taken`, `is (already) held`, `is already claimed` or `(is) claimed|held|taken by …` reports who holds it and is no claim either (also on a line an older log stored as one); `is mine now, starting` is a claim. In the clause, sentence and `[CLAIM]` forms the target is one word (after an optional role word), never `the`, `my`, `a`, `an`, `it`, `this` or `that`. A release takes its sender off each of its own claims whose target its text names before its first sentence end or `[CLAIM]` (by path, file name, the name without extension or its leading number: `[RELEASE] parser, lexer`, `[WITHDRAW] t3 withdraws the 06-parser claim`); a `[CLAIM]` later in the same message (`[RELEASE] parser. [CLAIM] research lexer`) is a claim. A release also forgets the sender's `is yours` for those slices, so claiming one again is answered again. Each message is read once, when it is logged, for roster.json, the list and the looks alike: a broadcast `[CLAIM]` an idle teammate takes after its sender's release undoes nothing. Nothing else releases a claim (`commit lock released`, `I handed the draft…`, `I release the mutex in x.ts`, `I withdraw my objection`, `core.ts is released to review` do not). A `[DONE]` naming a slice (to anyone, the lead too) shows that slice's card as `DONE` in the looks, a research slice too, until it is claimed again; a `[DONE]` naming none marks the sender's build and research slices. A report closes the sender's claims per slice: a `[DONE]` closes the sender's claims on the slices its first line names, a `[REVIEW]` its review claims on them (`[REVIEW] joins-leaves …` from its builder closes no review), one naming no slice on the board every claim (`[DONE]`) or every review claim (`[REVIEW]`) of the sender, a `[BLOCK]` none; the sender's other claims stay open on the board, in roster.json and in the looks, so a builder that reviews another slice still holds its own. A later claim (a build or research claim that found a holder, answered `is already claimed`, or a review claim on a slice a live teammate already reviews) lapses at its sender's next report of any type or next `[CLAIM]` of another slice, so a claimant that moved on in prose holds nothing stale. A reload restores this session's claims, deliverables and fired watchdog alerts from roster.json and the log. Once every teammate has ended (completed, failed, killed, or gone from `$.agent.list()`), the mod clears that team's message claims, verdicts, deliverables and fired alerts (`claimsSince` in roster.json; a reload replays only claims logged since); a task-list owner claims only while it is a live teammate.

### Claim conflicts

Inform, never enforce. A teammate whose `[CLAIM] build` or `research` names a target nobody holds gets one `swarm: <role> <target> is yours.` from the mod, once per teammate and slice, however it spells the target again (kept across a reload in roster.json `ackedClaims`). A `[CLAIM] build` or `research` on a target another teammate already holds, by an earlier claim or as the live owner of a task on it not completed (a task owner holds first; the claimant's own task is no conflict) (the same `#<n>`, a path that ends the other at a folder boundary, or a file name and a path ending in it, so `design.md` and `docs/design.md` match but `docs/notes.md` and `src/notes.md` do not; other words only when the whole targets are equal) is recorded under the first claim, shown with `⚠ duplicate` while both still hold it (a holder that ended, released it or reported on it no longer does: see Claims), and its sender gets one `swarm: [ASK] <target> is already claimed by <name> (<id>, since <time>, #<stamp>). Talk to them, split it, or pick another slice.` from the mod, ending in up to 3 slices nobody holds yet when the mod knows any (deliverables without a build or research claim, then unowned tasks: `… or pick another slice: docs/a.md, docs/b.md.`), with a second line `If you wait instead, the mod tells you when it passes to you.` (kept across a reload in roster.json `askedTaken`); the holder is the lowest stamp. A slice works as a lock (`merge-lock`): when its holder releases it (a report closing the holder's claim hands it to nobody: the slice is finished), the claimant who now holds it first gets `swarm: <role> <target> is yours.`, once however many teammates the release went to, and a later claim on it is answered again. A report or a review claim that ends a wait (a later claim lapses: see Claims) gets one `swarm: [ASK] you no longer wait for <role> <target>: a report ends a wait. Claim it again to wait.`; a claim of another slice ends it silently. Claiming a slice again after one's claim on it closed queues by the new claim's stamp. A release naming a slice that others hold and its sender does not frees nothing; its sender gets one `swarm: [ASK] you hold no <role> <target>: <name> (<id>) does. Your release released nothing.` A teammate's Edit, Write, MultiEdit or NotebookEdit on a file other teammates hold a build claim on goes through; afterwards the writer gets `swarm: [ASK] you wrote <path>, claimed by <name> (<id>). Settle it with them.` and the first holder a copy, at most once per writer and file every 2 min.

### Claim TTL

A claim whose holder has sent nothing for 10 min shows as `stale` in CLAIMS (`#7 · build t1 stale`). It stays open: the stall nudge covers it.

### Claim watchdog

Once the team is a swarm, wakes the lead once per condition, coalesced, never mid-turn: a teammate sent `[DONE]`/`[HANDOFF]` while no `[CLAIM] build` names a deliverable (a swarm with no `Deliverable:` line and no `/swarm deliverable` has none to miss: no wake, no band `⚠`), or 2+ teammates have each worked without any claim for N minutes since their own spawn (else first message; default 3, `/swarm claim <min>`, 0 = off; a teammate that sent a `[CLAIM]` since its spawn and released it has claimed) → `swarm: no builder claimed for <deliverable>`, or `swarm: N teammates working without a [CLAIM]: …` (asking for `[CLAIM] <role> <slice>` when the swarm has no deliverable, for a builder when it has).

### Wait wake

A teammate about to launch a background command it may go idle on sends `[WAIT] <absolute path>` (the file that command writes last; the path ends at the first space, a path with spaces goes in backticks). Its latest wait is kept in roster.json across reloads and fires however long the teammate stays idle; a teammate holding one is never dormant. Every 10 s, for each idle teammate (an idle notice and no message since) with a wait, the mod stats the file; when its mtime is newer than the start of the turn that sent the wait (the teammate's last idle notice, else its spawn) and than the last wake, it sends that teammate `swarm: [ASK] <path> changed: <first 200 characters, one line>` with `$.session.send({ to: { agentId } })`. `[WAIT] until <ISO-8601 time>` is the second form: the idle teammate gets `swarm: [ASK] <time> reached: the time your [WAIT] named` once that time has come. A `[WAIT]` addressed to the lead is not delivered: the `session.send` hook answers `{ isDelivered: false, reason }`, and the teammate reads that the wait is registered.

### Stall watchdog

Every 2 s, once the team is a swarm: no message and no agent running/pending/waiting for M minutes (default 5) while work remains: an open claim of a live teammate, or open tasks (an empty task list with an open claim still counts). First it sends each live teammate holding an open claim (a `[CLAIM]` it has not released or reported on since) one `swarm: [ASK] quiet <M> min: you hold build src/parser.ts; reported: Sage (t2) REVIEW. Continue, or send [DONE]/[BLOCK].` Each open claim is nudged once, a teammate at most once per 10 min (a stall that finds a claim holder waiting out its cooldown waits with it, and nudges then), counted only when delivered; a report from its holder closes it, a re-sent `[CLAIM]` is a new one. When the swarm is quiet again M minutes after a nudge (chatter in between or not), or no un-nudged open claim is left, it wakes the lead with `swarm stalled`, once per quiet period.

### Work done

Every 2 s, once the team is a swarm and the lead is not mid-turn: when a `[DONE]` from a teammate of the current team (since the claims were last cleared) names every deliverable (`Deliverable:` lines, `/swarm deliverable`), or with none declared every build and research claim on the board (a `[DONE]` naming none of its sender's claims names each of them), no live teammate holds an open claim other than a review claim (a reviewer reports by its `[REVIEW]`s and `[DONE]`), no teammate's latest report is a `[BLOCK]` and no slice's review verdict is `✗block`, and every live teammate of the current team is idle (an idle notice after its last message), it wakes the lead with `swarm: all deliverables done, no open claims or blocks, every teammate idle; start the final review (protocol §3, phase 6) unless it ran, else stop_swarm when you agree.` (`every build and research claim done` with no deliverable). Once per last message (kept in `firedAlerts` in roster.json across reloads): a new claim or message re-arms it. It stops nothing; the lead decides.

## Lead wakes

### Lead filter

`quiet on` (default), once the team is a swarm: a delivery to the lead from a live teammate of the current team is logged, counted and run through every watchdog, then taken with `session.receive` → `{ consumed }` when it is an idle notice whose reason is `available` or absent, or a `[PROPOSE]`, `[CLAIM]`, `[HANDOFF]` or `[REVIEW]` that neither mentions `@lead` nor has a line starting `[ASK]` or `[BLOCK]`. Idle notices from a swarm's teammate that ended in the last minute, or from a teammate of a current team whose every teammate has ended (a team the lead stopped), however late they come, are taken the same way. So is an idle notice from any teammate, swarm or not, whose message reached the lead in the last 60 s: it repeats that report. Everything else reaches the lead: `[ASK]`, `[BLOCK]`, `[DONE]`, idle notices with a failure reason, untyped text, other sessions' messages and the mod's own wakes. The band shows `wakes N · held M`; the LEAD counts of look A and look B count the same wakes, the mod's own included, from the shown team's start.

### Wake

Wakes the lead with `$.prompt.submit` (framed as a message from the plugin, not the user). Modes: see [Wake modes](README.md#wake-modes-and-why-the-default-is-mentions). Once every teammate of the current team has ended, its messages still queued for a wake (`all`, `mentions`, `digest`) are dropped: they stay logged and wake nobody. The mode a session sets (`/swarm wake`, the pane's `a` `m` `d` `o`) is stored for that session and as the plugin's: a reload restores the session's own, though another session set another since; a new session starts with the one set last in any session.

## The pane

### `/swarm` pane

Look A by default: one card per agent of the current team with its full name, model, sent/received counts, state (running, idle, waiting on a `[WAIT]`, stalled) and time in it, the file it last edited, wrote or read (`✎ hooks/core.ts`, `◦ README.md`), and a bar of its tool calls and messages per time slot (a slot with a message and a tool call brighter; a log without tool-call lines counts messages only) coloured by its state, on one time axis for all cards (the message list gives up rows down to 3 to keep the cards; when they still do not all fit, every agent shows on one line instead, `▌● Atlas t1 RUNNING 1:04 Reading …` (at rich with a bar of 16 cells at the line's end, fewer on a narrow line and none under 6, on one time axis for all lines, the action cut first and left out under 8 cells), in two columns when needed, the last cell `+N more` only when even that does not fit); the claim cards (a double claim shows `⚠ duplicate` while both claimants hold it, BLOCKED only after a `[BLOCK]`; when the boxes do not all fit, every claim shows on one line instead, `■ docs/a.md Atlas OPEN` (a double claim `■ docs/a.md Atlas Kite ⚠ OPEN`, the names cut first), in the same columns, the message list giving up rows down to 3 first, the last cell `+N more` only when even that does not fit; a narrow pane lists up to 3 and the rest as `+N more`); the lead's wakes, delivered and held; the message list newest first, names in full, under a rule that sits right under the taller of the two columns (the lead block, or the last claim), so the message list takes the rows left (at 18 agents on one line each, every row under the lead block). A message moves through the cells for 0.7 s as it lands; nothing animates in between. The stage leaves room for the control row as it wraps (20 agent buttons take several rows) and for the wake-mode row, so both stay on screen. The pane opens with the keyboard (`/swarm` from an empty prompt; Escape hands it back and closes the pane). Buttons, each also a key while the pane has the keyboard: an agent's name filters to its threads and, in the live pane while that agent is live, shows under the stage a field `to Atlas (t1):` that takes the keyboard (type, Enter sends what `/swarm say t1 <text>` sends and shows `sent to Atlas (t1)` or why not; empty sends nothing; Escape hands the keys back to the buttons), then `Atlas (t1) · transcript` and the last 6 lines of its transcript (`$.session.messages({ agentId })`, read again every 2 s while shown: `› ` the user's first line, `‹ ` the agent's, `· <tool>` per tool call; one it cannot read shows `transcript not readable: <why>`); pressed again it clears both; keys `1` (look A) and `2` (look B, the team as a star map around the lead, wakes counted beside it, the claims as chips under it (`⚠` on a double claim): as many as fit the row, at most 6, then `+N more` for the rest, for watching and demos) and the `[ list ]` button (`l`, the text list below) switch the view; `a` `m` `d` `o` set the wake mode; `[ stop all ]` (`x`) stops every live teammate after one confirmation (see Stop the swarm). A replay's row has `[ live ]` (`0`) while a live team is active, the agents, then `[ nudge ]` (`n`), `[ pause ]` (`p`) and `[ stop ]` (`s`); `1` and `2` switch its look. The current team is the latest set of teammates that messaged each other, plus every teammate spawned after it formed while one of them was live (one that only writes to the lead too). A teammate that had stopped, or was dormant (started over 6 hours before with no message of its own in those hours, or whose last message is that old), never joins by receiving a peer message, only by sending one itself; so a hello to an earlier swarm's idle teammate does not pull it onto the cards, the map or the title (`t1–t18`). Before a team exists the cards show the live teammates. An ended team never wins over live teammates: once every teammate of the current team has ended, a live teammate outside it that is running, pending or waiting, or started after the team's last peer message, makes the cards show the live teammates instead (a new team forms from them).

### Pane level

`basic` draws text cells only; look B's basic sky (for terminals without pictures, such as Apple Terminal and tmux) paints the star map in half-block cells with 24-bit colour and braille edges on one flat dark backdrop across its box, so a terminal that rounds to 256 colours shows no bands: each message flies as a comet with its type riding quietly behind it (a burst as `claim ×5`, at most 6 words at once, each whole or left out where a node, the LEAD label or another word is in the way or right beside it), its edge lighting up behind it, a held comet splashing at the membrane and a delivered one flaring its receiver, frames only while something moves. `rich` adds pictures (the bars, the wake strip, the star map), each drawn again only when what it shows changed. The bars and the wake strip are raw pixels, at most once a second and 100,000 characters of base64 (about 75 KB) each. The star map is drawn at 10 × 20 pixels a cell (the types give a mod no cell size), at most 1,000,000 pixels; a larger box gets it scaled down. A message lights its edge on the star map, fading out over 6 s; every message of a burst lights its own edge. Where a python with numpy runs (the `skyPython` setting, else `python3` from PATH, else `uv run --no-project --with numpy python`), look B rich hands its sky to `hooks/sky.py`, a renderer process started the first time look B rich is shown and paused while it is not (another look, the list, a replay restarting); it leaves after 2 min without a scene and starts again when wanted: the mod writes the scene (agents, edges with their weights, lit edges, wake counts and comets, in the picture's pixels) to a temp folder (`$TMPDIR/swarm-<session>`) when it changes, and draws no picture itself; the renderer paints the whole star map, the backdrop once per size, at up to 30 frames a second while a comet flies or a lit edge fades (about 10 ms a frame at 860 × 620), and writes each frame to a file, and the pane shows each frame by naming that file, so the terminal reads the pixels itself; idle, no frame is drawn. Until the first frame the box shows the sky's dark ground. The renderer removes its files when it ends. When no python with numpy runs (`/swarm status` names each one tried and why), the renderer crashes twice, or the terminal says it cannot read files or draw pictures, look B draws the basic sky for the session and says why in one dim line under the stage (`basic sky: the sky renderer failed (no python with numpy: …)`); `/swarm status` says it too. The sky stands on its own dark colour, so a terminal that fits it inside its box shows no grey bars. A comet's edge lights up behind it as it flies, a pair's first edge drawn only as far as its first comet got; a comet the lead filter holds stops at the membrane with a ripple, one that reaches the lead flares the sun. Each wake that reached the lead adds a ray around the sun, each held one a bead on the membrane, at most 24 of each; from 24 delivered wakes on, their number shows in the ring under the sun. When a comet lands, its type shows under the receiver's name for 1.5 s, a burst bundled (`claim ×3 · handoff`). A terminal whose cells are not 1:2 fits it with thin bars. On recorded runs played live that came to 0.04–0.34 MB a minute for look A and 0.29–2.32 MB for look B; look B's ceiling is 9 MB a minute. With `/swarm level auto` (the default) the pane draws one 1×1 picture and goes rich when the terminal shows it (a blit taken), basic when the terminal says it draws no placeholder images; any other refusal (no image id free) keeps it basic and is asked again, at most three times.

### Text list

Roster with live status, model as family and version (`opus 5.5`; `–` when `agent.spawn` never reported one), sent/received counts and `waits N · 40s ago` (an agent without a name shows its spawn description); a subagent a teammate spawned (`agent.spawn`'s `parentAgentId`, or the agent list's `parentId`; roster.json keeps it as `parentId`) shows right under that teammate as `└ ● scan the repo running` until it ends, then under `── other agents ──`; a teammate idle past the stall minutes while holding an open claim shows `! … stalled`. Active teammates come first; agents outside the current team, completed, failed or killed, dormant teammates (idle for over 6 hours, holding no wait or claim; see Ended team), or pending for over 10 min, show dimmed under `── other agents ──`: the newest 5, after a `… N more` line when there are more (a previous session's agents under `── earlier ──` the same way). The last N messages newest first (`from → to: first line`), a previous session's below them under `── earlier ──`, time since the last message, wake-mode buttons (`a` `m` `d` `o`). N is what the pane's rows leave after the roster and the claims; the list never runs past the pane's rows, so the view buttons and wake-mode buttons below it stay on screen. Lines are cut to the pane's `bodyColumns`.

### Band

One line above the prompt once a swarm is active: `swarm: 4 agents · 12 msgs · last 8s · wake: mentions · wakes 3 · held 9 · Atlas (t1), Sage (t2)`; the agent count is the current team's agents that have not ended, the names are the current team's only.

### Status line

While the current team is a swarm, the mod's status line under the prompt reads `◇ swarm 3 live · 1 done` (`· 1 failed` when any failed), counted over the team's teammates: live are those that have not ended, done those that sent a `[DONE]` since they started and no `[CLAIM]` after it (a new claim takes one out until its next `[DONE]`), live or not (a reload counts this session's log); pinned again only when it changes (checked every 2 s); it clears when the team ends.

### Stand-down toast

Once the last teammate of a swarm has ended, one toast, shown for 20 s, with its totals: `swarm stood down: 4 agents · 52 messages · 12m · lead woken 3 (0.8/agent), held 18` (messages to or from its teammates since its start, the mod's own not counted; its time from the first spawn of its teammates to its last activity, the span the ENDED header shows as `ran`; the lead's wakes and held deliveries during it, the wakes also per agent as the swarm's health number). Once per team, and only for a team that was a swarm.

## Stopping and the protocol skill

### Stop the swarm

The mod registers the tool `stop_swarm` (`mcp__agent-swarm__stop_swarm`, input `{ names?: string[] }`) for the lead: it stops every live teammate of this session, or the teammates `names` gives (team or code names), each with `$.tool.call({ tool: "TaskStop", task_id: <name> })`, which goes through the permission check like the model's own calls. Only agents spawned as teammates; never another subagent (a builder, a checker) or a workflow's agent. It answers one line, `swarm: stopped Atlas (t1), t2 · failed t3 (<reason>)`; each stopped teammate is marked ended at once, so the pane shows the team as ended. The person has two doors to the same stop: `/swarm stop all|<name>`, and the live pane's `[ stop all ]` (`x`, shown while a teammate is live), which asks once (`Stop all 4 live teammates (…)?`) before it stops them. A call from a teammate stops nothing and answers `stop_swarm is the lead's`. A stopped teammate that a message reaches starts again (a new TaskStop task, the same agent id): the roster shows it live under its name once more, and the next stop stops it again. The mod never stops anything on its own.

### Skill `swarm-protocol`

The protocol the lead follows: brief (goal / constraints / budget / kill criterion / done), self-chosen code names, phases, `[TYPE] subject` messages, builder decides / reviewer vetoes / tie to lead, a build or research claimant ends its turn and starts on the mod's `swarm: … is yours.` (or, with no answer after one idle turn, on being the first holder in roster.json; a review starts at once; a lock slice such as `merge-lock` is waited on until the mod hands it over with `is yours.`), code built in a worktree per slice and merged holding `merge-lock`, never released with the integration branch red, building less than the claim said announced with a `[PROPOSE]` before the handoff and checked by the reviewer against the claim, no waiting for a clock time (`[LOCK]` once every open claim has reported, `[WAIT]` before idling on a background command), 3–7 agents, fresh-agent synthesis.
